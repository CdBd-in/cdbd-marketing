BG_SLOT(opacity 20% 풀 배경)도 ❌.
> **🆕 기능 이미지 fit-by-height + 우측 정렬** (2026-06-04): 기능 이미지 fill 시 **이미지 비율 유지 + 슬롯 세로(height) 가득 채우기**. `scaledW = imgW × slotH / imgH` 계산 후 분기:
> - **scaledW > slotW (wider, overflow)** — 슬롯 크기 유지, `scaleMode = "CROP"` + `imageTransform = [[slotW/scaledW, 0, 1 - slotW/scaledW], [0, 1, 0]]`. 좌측 overflow 잘림, 우측 데이터 보존.
> - **scaledW ≤ slotW (narrower)** — 슬롯 자체를 `scaledW × slotH`로 **resize**, 우측 정렬 위치로 이동, `scaleMode = "FILL"` (slot 비율과 image 비율이 같으므로 왜곡 ❌). 우측 정렬 기준은 **mockup left edge** (mockup과 슬롯이 겹치는 레이아웃, 예: B 상단형) 또는 **원 슬롯 right edge** (mockup과 안 겹치는 레이아웃, 예: B 하단형).
> 적용 대상: 위 cornerRadius 규칙과 동일 (B EDITOR_SLOT 등 기능 이미지 모두). 시각적 의도: 답변/통계 캡쳐는 우측에 핵심 데이터(차트·답변 수)가 위치 → 우측 정렬이 의미 보존에 유리. 예약카드 같은 portrait 위젯도 우측 정렬되어 mockup과 시각적 흐름 형성.

- **비율 매칭 기반 식별**:
  - 원페이지(338:3224) → 단일 screen rect 0.4535 → 그대로 fill
  - 멀티페이지(338:3238) → 2개 fillable rect 중 **0.6531에 가장 가까운 rect** (중앙 띠)만 fill / 다른 rect(0.4392 phone)는 master 원본으로 복원

```js
// 정확한 mockup screen 식별 의사코드
const rects = mockup.findAll(n => n.type === "RECTANGLE" || n.type === "FRAME");
const TARGET_RATIO = mockupName === "338:3238" ? 0.6531 : 0.4535;  // mockup 종류별
let best = null, bestDiff = Infinity;
for (const r of rects) {
  const diff = Math.abs(r.width / r.height - TARGET_RATIO);
  if (diff < bestDiff) { bestDiff = diff; best = r; }
}
best.fills = [{ type: "IMAGE", imageHash, scaleMode: "FILL" }];
```

#### 1.1.c. CROP imageTransform 비율 보존 공식 ⭐ (2026-06-12 추가, 사고 사례 기반)

> **사고**: A 안 2 / C 안 1·2에서 풀페이지 캡처(750×8090, aspect 10.79)를 mockup screen(aspect 2.21)에 `imageTransform: [[1,0,0],[0,1,0.55]]`로 fill → 비율 깨져 모자가 가로 늘어남.
> **원인**: `imageTransform`의 매트릭스는 **슬롯 좌표 → 이미지 좌표 매핑**. y-scale을 1로 두면 이미지 세로 비율 무시 → stretch.

**올바른 매트릭스**:

```
y_scale = slot_aspect / image_aspect
ty 범위 = 0 ~ (1 - y_scale)
imageTransform = [[1, 0, 0], [0, y_scale, ty]]
```

여기서:
- `slot_aspect` = `screen.height / screen.width` (mockup screen rect 비율)
- `image_aspect` = `image.height / image.width` (캡처 원본 비율, `getImageByHash().getSizeAsync()`로 측정)
- `ty` = 콘텐츠 영역의 Y 비율 (0 = 이미지 상단, max = 이미지 하단 직전)

**Plugin API 사용 예시**:

```js
// 1) 이미지 size 측정
const imgSize = await figma.getImageByHash(imageHash).getSizeAsync();
const imgAspect = imgSize.height / imgSize.width;

// 2) screen aspect 측정 (mockup INSTANCE 안의 흰색 rect)
const slotAspect = screen.height / screen.width;

// 3) y-scale 계산 + ty 결정 (콘텐츠 의미 영역)
const yScale = slotAspect / imgAspect;
const ty = 0.55;  // 룩북 카탈로그 (이미지 55% 지점)

// 4) CROP + 비율 보존 매트릭스
screen.fills = [{
  type: "IMAGE",
  imageHash,
  scaleMode: "CROP",
  imageTransform: [[1, 0, 0], [0, yScale, ty]],
}];
```

**ty 결정 — 의미 영역 매핑 (§1.1.b 의미 영역 크롭)**

| 이미지 콘텐츠 위치 | ty 값 (image_aspect=10.79 가정) |
|------------------|-----------------|
| 상단 hero | `0.00 ~ 0.05` |
| 본문/안내 | `~0.20` |
| 중간 콘텐츠 (룩북·상품 grid) | `0.45 ~ 0.55` |
| 하단 (인물·CTA) | `0.65 ~ 0.75` |
| 최하단 (RSVP·푸터) | `0.78 ~ max` |

> max = 1 - y_scale (이 값 초과 시 이미지 끝을 넘어가 검정 영역 표시됨)

**주의 — sparkle·crown 데코 컴포넌트는 별개** ⛔:
- 데코 INSTANCE 안에도 IMAGE fill을 가진 RECTANGLE/FRAME이 있음 (sparkle PNG·crown PNG 등)
- 자동화가 mockup screen만 노려야 하는데 **데코 instance 내부 rect까지 잡으면** y_scale 매트릭스가 데코에도 적용되어 시각 오류 (crown이 가로 늘어남 등)
- **방어 3종 (필수 적용)**:
  1. **mockup INSTANCE 이름 필터**: `instance.name === "원페이지 목업-1"` 또는 `instance.name === "MOCKUP_MASTERS"` 등 정확한 이름 매칭. `instance.name === "sparkle2"` 같은 데코는 제외
  2. **mockup fill 처리 후 데코 추가 순서**: 1) mockup INSTANCE 생성 → 2) screen rect 찾기 + IMAGE fill (CROP + 비율 보존 매트릭스) → 3) **그 다음** 데코 INSTANCE 생성·배치. 순서 보장하면 mockup 처리 시 데코는 존재하지 않음
  3. **PNG/SVG 컴포넌트는 그대로** — 데코 INSTANCE는 createInstance() 후 rescale만, IMAGE fill 건드리지 않음

**자동 적용 워크플로우 (use_figma 모드 권장 시퀀스)** ⭐:

```
1. 슬롯 페이지에서 슬롯 frame clone → 출력 페이지 appendChild
2. 텍스트 fill (TITLE/SUBTITLE)
3. mockup INSTANCE 생성:
   a. createInstance(338:3224 또는 338:3238)
   b. visualSlot.width로 rescale
   c. visualSlot.x/y로 이동
   d. visualSlot.effects 복사 (보라 글로우 등)
   e. screen rect 찾기 (회색톤 RECTANGLE/FRAME, 멀티페이지면 비율 0.6531 분기)
   f. ⭐ 이미지 size 측정 + y_scale 계산
   g. CROP + 비율 보존 매트릭스 fill
4. mockup INSTANCE 처리 완료 후 데코 INSTANCE 생성·배치 (DECO 슬롯 위치)
5. placeholder 제거 (visualSlot.remove() 등)
```

→ 이 순서면 비율 보존 매트릭스는 mockup에만 적용, 데코는 영향 없음.

```js
// 예시 — 회색톤 + 밝기 0.9 이상 (FFFFFF·FAFAFA 모두 포함)
// 🆕 2026-06-12: use_figma MCP 환경은 sync getNodeById 미지원 → async 사용
const mockup = (await figma.getNodeByIdAsync("338:3224")).createInstance()
const screen = mockup.findOne(n => {
  if (n.type !== "RECTANGLE" && n.type !== "FRAME") return false
  const f = n.fills?.[0]
  if (f?.type !== "SOLID") return false
  const { r, g, b } = f.color
  const isGray = Math.abs(r-g) < 0.05 && Math.abs(g-b) < 0.05
  return isGray && r >= 0.9
})
screen.fills = [{ type: "IMAGE", imageHash, scaleMode: "FILL" }]
```

##### 🆕 C 멀티 목업 — 단일 페이지 viewer를 의미 섹션 3개로 분할 (2026-06-12 INHA 시안 신규)

> C 유형(`338:3150` 멀티·상단·서브)은 본래 멀티페이지 viewer(swiper)용이지만, **단일 페이지 viewer를 의미 섹션으로 잘라 3개 mockup에 각각 다른 영역으로 fill**하는 패턴도 가능. 타이틀이 "한 페이지에 여러 섹션이 다 들어있다"·"행사 흐름" 류일 때 강력.

**적용 조건**:
- **단일 페이지 viewer** (스크롤형) — 멀티페이지 swiper면 [[#2. 템플릿 카탈로그 — A·B·C 공용 (Microlink 캡처 가능)\|이미지 출처 §2]] 멀티페이지 mockup 그대로
- 타이틀이 **여러 기능·여러 시간대·여러 단계** 등 **복수 의미**를 함축
- 사람 관점에서 viewer를 봤을 때 자연스러운 **사용자 여정 3단계**가 보임 (정체성 → 핵심 정보 → 액션)

**절차**:
1. **사람 관점 viewer 분석** — 브라우저로 viewer 열어 의미 섹션을 사람이 직접 파악 ([[1-1-4. 검수 체크리스트|2]] §자주 놓치는 #10). 자동 캡처만으로 결정 ❌
2. **3개 의미 섹션 선정** — 자연 흐름:
   - **섹션 1**: 정체성 (hero — 브랜드/행사 정체성·포스터·로고)
   - **섹션 2**: 핵심 정보 (타이틀이 직접 가리키는 그 정보 — 예: 시간·일정·기능 디테일) ⭐
   - **섹션 3**: 액션 (RSVP·구매·문의·CTA 등 사용자 참여 영역)
3. **mockup aspect (≈0.4535)에 맞춰 PIL crop** — 각 섹션을 `width=원본_w / height=원본_w / 0.4535 ≈ 원본_w × 2.205`로 잘라야 mockup screen 안에 비율 보존되어 들어감
4. **3개 PNG 업로드** — `upload_assets(count=3)` 한 번에 3개 hash 확보
5. **각 VISUAL_SLOT_1/2/3에 mockup instance + 해당 hash fill**:
   - `mockupMaster.createInstance()` → `rescale(slot.width / mockupMaster.width)` (예: 143/197.36 ≈ 0.7246)
   - screen rect 찾아 `scaleMode: "CROP"` + 비율 보존 매트릭스 fill
   - 위치를 slot.x, slot.y로 이동 + 슬롯 placeholder hidden + strokes/fills 제거

**PIL crop 의사코드**:
```python
from PIL import Image
im = Image.open('viewer-fullpage.png')
W, H = im.size  # ex: 640 × 5910
SEC_H = int(W / 0.4535)  # ex: 1411

# Sections by y range — 사람 분석 결과
sections = [
    ('sec1-hero',   0,    SEC_H),       # 정체성
    ('sec2-core',   2533, 2533 + SEC_H), # 핵심 정보 (타이틀이 가리키는 그 섹션)
    ('sec3-action', 3944, 3944 + SEC_H), # RSVP/CTA
]
for name, y0, y1 in sections:
    im.crop((0, y0, W, y1)).save(f'.temp/{name}.png')
```

- **Mockup 1 (좌, sec1)**: y=0~1411 → 포스터 + "40th Inha Univ. GRADUATION FASHION SHOW" — 행사 정체성

## 3. 기능 라이브러리

> **핵심 인사이트**: CdBd 자체가 "기능 조합으로 만든 페이지". 따라서 **viewer 페이지의 한 섹션 = 해당 기능의 라이브 데모**.
> 5유형 매핑:
> - **§3.1 viewer 기능** = **A. 목업 전용** (발행 페이지에 보이는 기능) — Microlink 자동 캡처 가능 (15개)
> - **§3.2 에디터 기능** = **B. 목업+에디터 전용** (편집·관리 화면 기능) — Playwright 캡처 (8개 우선 후보)
> - **§2 템플릿 카탈로그** = **A·B·C 공용** (모든 목업 종류 출처)

### 3.4. 외부 사례 — viewer 카탈로그 외 케이스 ⭐ (2026-06-12 추가)

> CdBd 자체 카탈로그(§2의 17개 viewer)에 없는 사례를 다룰 때 — **사용자에게 외부 URL을 명시적으로 요청**해서 캡처.
> 카탈로그 매핑이 가능한 경우엔 **카탈로그 우선** — 외부 URL은 정말 매칭 없을 때만 fallback.

#### 적용 대상 — A · C 유형 한정

| 유형 | 발생 케이스 | 신호어 |
|------|-----------|--------|
| **A. 목업** | 외부 사이트·타사 사례·클라이언트 사이트 단일 인용 | "X사 사례", "어떤 브랜드의 ~", 카탈로그(§5.2)에 없는 사명·고유명사 |
| **C. 멀티 목업** | 비교·벤치마크·다중 사례 (CdBd ↔ 외부 혼합 또는 전부 외부) | "A vs B", "Best 3", "비교", "벤치마크", 카탈로그 외 사례 N개 |

> B·D·E는 외부 URL 룰 적용 안 함 — B는 에디터 UI(내부 전용), D는 Thiings 카탈로그, E는 Lexica AI 자동 생성으로 흐름이 다름.
> (D 유형 Thiings 슬러그 모를 때만 별도 PNG URL 요청 — §4.1 참고)

#### 절차

1. **사용자에게 URL 요청** — 명시적으로 묻기:
   - A 유형: "썸네일에 들어갈 viewer URL을 알려주세요"
   - C 유형: "비교할 사이트 N개의 viewer URL을 알려주세요 (순서대로)"
2. **Microlink 캡처** — 유형별 viewport 정책 동일하게 적용:
   - A 유형: `viewport.width=375 / height=812 / full-page=true` (모바일 풀페이지)
   - C 유형: `viewport.width=375 / height=900 / full-page=false` (hero 캡처 — §7.2 표준 패턴)
3. **upload_assets → imageHash 확보** (use_figma 모드)
4. **fill 흐름은 카탈로그 매핑과 동일** — §3.3 Step 3-5 따라감 (A: 단일 fill / C: VISUAL_SLOT_1/2/3 분배)
5. **fallback** — URL 미제공 시:
   - A: §1 Step 4 fallback (카탈로그에서 가장 가까운 사례 3개 제안)
   - C: 카탈로그 사례로 부족분 대체, 그래도 부족하면 사용자에게 다시 요청

#### 주의

- **저작권·이용 정책 확인 필요** — 외부 사이트 캡처 사용은 사용자 책임. 클라이언트 사이트는 협의된 사례인지 확인.
- **카탈로그 우선 원칙** — §5.2·§5.4 매핑 가능한 경우 외부 URL ❌. 정말 매칭 없을 때만.
- **한 시안 안 혼합 OK** — 특히 C 유형 비교 시 CdBd 사례 + 외부 사례 혼합 자연스러움.
- **자동화 체크리스트 §자주 놓치는 #2 "가이드 표 그대로 사용"과의 관계** — 카탈로그에 있는 사례를 외부 URL로 대체하는 건 ❌ (가이드 우선). 카탈로그에 없는 사례만 외부 URL.

## 7. Figma 이미지 적용 시 주의사항 (2026-05-26 발견)

> `upload_assets` MCP에 `nodeId`를 지정해도 fill이 **자동 적용되지 않음**.

### 7.1. 기본 패턴

### 7.2. Microlink viewer 캡쳐 표준 패턴 ⭐ (2026-05-31 확정)

> **문제**: Microlink 모바일 뷰포트(375×812) full-page 캡쳐 시 viewer 페이지 외곽에 **검정 padding이 4면에 추가됨** (위·아래 ~250px, 좌·우 ~60px @1320×3034 기준).
> **잘못된 해결**: Python으로 검정 영역 잘라내기 → viewer 자연 여백까지 손실 (v10). 흰색 치환 → viewer 배경색과 불일치 가능 (v11).
> **올바른 해결**: **원본 캡쳐를 그대로** Figma 업로드 + **scaleMode CROP + imageTransform**으로 viewport 시각적으로 안쪽 영역만 표시.

```js
// 자동화 표준 (code.js의 applyMockup 함수)
screen.fills = [{
  type: 'IMAGE',
  imageHash: '<원본 v8 hash, 픽셀 처리 X>',
  scaleMode: 'CROP',
  imageTransform: [
    [0.9078, 0, 0.0461],  // 좌우 4.61%씩 crop (가로 90.78% 영역만 사용)
    [0, 0.8907, 0.0859],  // 위 8.59% (status bar 영역) + 아래 2.34% crop
  ],
}];
```

**imageTransform 매트릭스 해석**:
- `[[sx, 0, tx], [0, sy, ty]]` — 표시할 영역의 비율(sx·sy)과 시작 offset(tx·ty)
- 원본 1320×3034 캡쳐 → x=60.85~1259.15, y=260.62~2962.61 영역만 화면에 표시
- 검정 padding은 viewport 밖으로 밀려나 자동으로 안 보임

**장점**:
- 픽셀 처리 단계 제거 → Python `Image.crop()` 불필요
- 단일 원본 hash 재활용 (동일 viewer 여러 슬롯에 적용 시 hash 1개만)
- 캡쳐 도구 차이(Microlink padding 변경 등)는 매트릭스 값만 조정

**모든 viewer 캡쳐가 동일 매트릭스 사용 가능한지**: Microlink가 viewport 비율과 캡쳐 페이지 비율 차이로 padding을 생성하므로, 같은 모바일 뷰포트(375×812)면 모든 viewer가 비슷한 padding 비율을 가짐. 다른 viewport 또는 다른 캡쳐 도구 사용 시에는 매트릭스 재측정 필요 (참조 frame의 imageTransform 추출 → 그 값으로 갱신).

**참조 frame**: `83:186` "원페이지 목업-1" (사용자 작성, 슬롯 페이지) — 매트릭스 값의 원본 출처.
