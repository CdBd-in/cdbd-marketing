# §0 단계 0: 입력 분석 (사전 3원칙 진입 전 필수, 2026-06-18 신설)

> **타이틀만이 아니라 타이틀+본문 입력 시대로 전환.** 본문이 유형·자산·강조어 결정의 1차 근거.
> 첫 시험 사례: [[2026-06-18 PDF·플립북 카탈로그의 한계]] / 검증 2회: [[2026-06-19 VIP 200명 1:1 개인화 초대장]] · [[2026-06-19 50인+ 전사 도입 명함 ROI]]

## ① 입력 형식 확인
- **타이틀 + 본문**: 본문 구조 분석 전체 적용
- **타이틀만**: 본문 구조 분석 건너뜀. em dash·강조어 길이 검사는 동일

## ② em dash / marker 분리 검사
- 타이틀 안 `—`(em dash) / `-`(hyphen) / `/`(슬래시) 또는 시리즈명 marker → **SUBTITLE/TITLE 분리 후보**
- marker 있으면 **사용자 컨펌** (서브타이틀 슬롯 변형 선택 결정)
- ⛔ 원본 텍스트 변경 ❌ — marker는 분리 기호로만 활용, 양옆 공백만 trim

## ③ 본문 구조 분석 → 유형 격상
- 본문 구조 신호(대비 구조→C 멀티 / 단일 사례 시연→A / 선언·정의·주장→D)로 유형 격상. 본문 신호 약하면 타이틀 신호어 매칭.
- 📌 캐논 규칙·신호 표 → [[1-1-2-1. 레이아웃 규칙]] §1.1 "본문 구조 분석 → 유형 격상"

## ④ 자산 직접 매칭 (가이드 우선)
- 본문이 [[1-1-3. 이미지 규칙]] §5.2 17개 viewer 중 하나를 **명백히 가리키면** → 1순위 자산 확정 (추측 ❌)
- 본문 §정의/설명과 viewer §2.x 설명이 1:1 매칭되는 경우만
- 예: "문의로 이어지는 동선" ↔ `catalog/oak_table` "제품 정보 전달과 고객 문의 연결"

## ⑤ 강조어 길이 사전 측정 ⭐ (사고 #1 방지)
- **공식**: `Array.from(강조어).length × 30px ≤ 슬롯 TITLE width`
- ⚠️ **char count 정확 측정** — `emphasis.length` 또는 `Array.from(emphasis).length`. 한글 자모 단위로 직관 카운트 ❌
  - 예: "1:1 개인화 초대장" = `1·:·1·공백·개·인·화·공백·초·대·장` = **11자** (자모 단위 9자 ❌)
  - 예: "인당 월 500원" = `인·당·공백·월·공백·5·0·0·원` = **9자**
- **TITLE/SUBTITLE**: 전 유형 hug(자동 폭)
- **초과 시**:
  - C 슬롯 → hug(자동 폭)로 한 행(1줄) 수용 (mockup_2 y=199와 시각 분리)
  - D/A 슬롯 → fontSize 36→32 축소 또는 강조어 단축 (사용자 확인)
- **사례**: "진짜 모바일 카탈로그"(10자) × 30 = 300px → 강조어가 슬롯 width 안에 한 줄로 들어가는지 사전 측정

## 4-A. mockup·DECO instance z-index — DECO는 항상 z-top ⭐ (사고 #12)

`frame.appendChild()`로 노드 추가하면 children 배열 마지막이 z-top. mockup을 마지막에 추가하면 **DECO가 mockup 아래로 가려짐** ⛔.

**children 표준 순서** (z-top → z-bottom):
1. **DECO instance** (sparkle·crown·envelope — 최상단)
2. mockup instance (338:3224 등)
3. VISUAL_SLOT / VISUAL_SLOT_1·2·3 (placeholder, fills 비움)
4. EDITOR_SLOT (B 유형)
5. TEXT_BLOCK / TITLE / SUBTITLE

**자동화 순서**:
```js
// ① 텍스트 fill (TEXT_BLOCK 위치)
// ② mockup instance 추가 (가장 위에서 시작)
frame.appendChild(mockupInst);
// ③ DECO instance 추가 또는 기존 데코를 z-top으로 재정렬
const deco = frame.findOne(n => n.type === "INSTANCE" && 
  (n.name === "crown" || n.name === "envelope" || ...));
if (deco) frame.appendChild(deco);  // 다시 appendChild → children 마지막 → z-top
```

**검수**: 빌드 직후 데코가 mockup 위에 보이는지 시각 확인. mockup 베젤 위로 데코 우측 일부가 살짝 걸쳐 보여야 정상 ([[1-1-2-1. 레이아웃 규칙]] §2.4)

> 사고 사례: 2026-06-19 VIP A1·A2 — mockup 추가 후 crown·envelope 데코가 그 밑으로 가려짐 → `appendChild(deco)` 재정렬로 해결

## 4-B. instance child mutate 패턴 ⭐ (2026-06-19 신규)

**증상**: A·B 유형 mockup instance(338:3224) 자식 screen rect에 viewer 이미지 fill 적용했는데 mockup 마스터 기본 image가 그대로 보임.

**원인**: `mockInst.findAll/findOne`로 얻은 child reference에 `.fills = [...]` 적용해도 instance override 작동 ❌. use_figma MCP 환경 특수 제약.

**해결 패턴** ⭐:
```js
// ❌ 작동 안 함
const screen = mockInst.findOne(n => n.fills?.some(f => f.type === "IMAGE"));
screen.fills = [{ type: "IMAGE", imageHash: HASH }];

// ⭕ 작동함 (ID 재취득 후 mutate)
let screenId = null;
for (const c of mockInst.children) {
  if (c.fills?.some(f => f.type === "IMAGE")) {
    screenId = c.id; break;
  }
}
const screen = await figma.getNodeByIdAsync(screenId);
screen.fills = [{ type: "IMAGE", imageHash: HASH }];
```

**적용 범위**: A·B mockup screen rect / C mockup 3개 각각 screen / 모든 instance 자식 노드 mutation

> 사고 사례: 2026-06-19 VIP A1·A2·B1·B2 — `findAll` 패턴 빌드 후 screen에 잘못된 image 보임 → `getNodeByIdAsync(screenId)` 패턴으로 해결

## 4-C. use_figma MCP API 제약 표

| API | plugin (정상) | use_figma MCP | 대체 |
|-----|--------------|---------------|------|
| `figma.getNodeById(id)` | ✅ sync | ❌ cross-page 미지원 | **`await figma.getNodeByIdAsync(id)`** |
| `figma.loadAllPagesAsync()` | ✅ | ❌ "not supported" | 제거 — `figma.root.children` 직접 |
| `figma.currentPage = page` | ✅ | ❌ "not supported" | **`await figma.setCurrentPageAsync(page)`** |
| `figma.createImageAsync(url)` | ✅ (manifest 등록) | ❌ "not supported" | `upload_assets` MCP + curl POST → `imageHash` |
| `fetch(url)` | ✅ manifest 등록 시 | ❌ "fetch is not defined" | 동일 — `upload_assets` 패턴 |
| `throw new Error()` | (변경 적용 후 throw) | ⚠️ 변경 rollback 가능성 | 검증·변경 분리 |
| `instance.findOne(...).fills = [...]` | ✅ direct mutation | ❌ override 누락 | **4-B** children 순회 + ID 재취득 ⭐ |

## 4-D. 자산 업로드 표준 패턴

1. PNG 캡처 → vault `.temp/` 저장
2. `upload_assets` MCP 호출 (count 최대 N) → 단일사용 submitUrl 받기
3. 각 PNG `curl -F file=@x.png` POST → response `imageHash` 추출
4. ⚠️ 업로드 부산물 = 임시 frame이 currentPage에 생성됨 → use_figma 코드 안에서 명시적 `remove()` 필요
5. use_figma 코드에서 imageHash를 mockup screen rect IMAGE fill로 적용
