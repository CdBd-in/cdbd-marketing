## 4. 발견·해결한 사고

### 사고 #1 — TITLE 어절 중간 wrap (해결)

**증상**: A1·D1·D2 초기 빌드에서 TITLE "1:1 개인화 초대\n장\n운영 가이드" 3줄로 강제 분리 — "초대장" 어절 중간 잘림 ⛔ (§텍스트 절대원칙 ② 위반)

**원인**: 강조어 "1:1 개인화 초대장" 9자 × 30 = 270px > 슬롯 TITLE width 285? 실측은 슬롯에 따라 다름 (338:3131 `TITLE` width 285 미만일 가능성). 한글 자모 조합 폭이 30px보다 클 수도. 결론: **285도 부족했음**.

**해결**: A·D 4안 모두 TITLE width 285 → **350 확장** + characters 재set + setRangeFills 보라 재적용 + A2 하단 변형은 TEXT_BLOCK y = 410 - height 재계산.

**룰 갱신 필요**: [[1-1-1. 스타일]] §3 TEXT 노드 폭 표에 "강조어 9자(+) 한 줄 fit 요구 시 A·D 350 확장 권장" 추가. PDF·플립북 사고 #1과 동일 패턴 — width 285 한계는 한글 8자 이내. ([[1-1-4. 검수 체크리스트]] §0 ⑤ + §자주 놓치는 #11과 일치)

### 사고 #2 — A2 슬롯 338:3107 텍스트 fill 실패 (해결, 룰 정착 필요) ⭐

**증상**: A2 초기 빌드에서 placeholder 텍스트 "서브타이틀 · 시리즈 #N" / "여기에 타이틀이 두세 줄로 들어갑니다" 그대로 노출 — 텍스트 fill 자체가 작동 안 함.

**원인**: 슬롯 `338:3107` 안 텍스트 노드 이름이 **`SUBTITLE`/`TITLE`이 아니라 placeholder 텍스트 자체**:
- `<text id="1:1249" name="서브타이틀 · 시리즈 #N">` (실제 노드 name이 placeholder text)
- `<text id="1:1250" name="여기에 타이틀이 두세 줄로 들어갑니다">`

→ `findOne(n => n.name === "SUBTITLE")`이 null 반환 → 텍스트 set 안 됨.

**해결** (위치 기반 fallback):
```js
const tb = f.findOne(n => n.name === "TEXT_BLOCK");
const texts = tb.children.filter(c => c.type === "TEXT").sort((a,b) => a.y - b.y);
const sub = texts[0];  // y 가장 작은 게 SUBTITLE
const ttl = texts[1];
// 노드 이름도 정상화
sub.name = "SUBTITLE"; ttl.name = "TITLE";
```

**룰 정착 후보** (P1 — 다음 세션 작업):
- §2.2 사용 절차에 **"슬롯 마스터 338:3107 노드 이름 정상화 필요"** 노트 추가 — 직접 슬롯 마스터에서 노드명을 `SUBTITLE`/`TITLE`로 rename
- [[1-1-4. 검수 체크리스트]] §자주 놓치는 추가 — "텍스트 노드 findOne 매칭은 name 기반 우선 + 위치 fallback (TEXT_BLOCK 자식 중 y 정렬)"

### 사고 #3 — A 슬롯 VISUAL_SLOT 자식 0개 (mockup instance 부재) ⭐ NEW (사용자 지적으로 발견)

**증상**: A1·A2 초기 빌드 후 사용자 지적 — "캡쳐 화면을 목업에 정확히 넣지 못하고 있어". mockup phone 베젤이 안 보이고 viewer 캡처가 빈 사각형에 직접 채워짐.

**원인**: 슬롯 마스터 `338:3131`(A 상단·서브)와 `338:3107`(A 하단·서브)의 VISUAL_SLOT(`240:236`, `240:238`)이 **자식 0개 빈 frame placeholder**. 가이드 [[1-1-3. 이미지 규칙|1-3. 이미지 규칙]] §1.1.a "applyMockup()" — 자동화가 mockup instance를 추가하고 그 안 screen rect에 fill해야 했지만, 초기 빌드 코드의 `fillA`가 VISUAL_SLOT 자체에 IMAGE FILL만 적용 → mockup 없이 viewer만 빈 사각형에 채워짐.

C 유형은 같은 코드에서 이미 `338:3224` mockup instance를 자동 추가하는 패턴 사용 → C5·C6 정상. **A 유형만 누락**.

**사용자가 정확히 가리킨 노드**: `454:339` = A2의 VISUAL_SLOT — 빈 frame에 personalized RSVP 캡처가 직접 fill되어 배경 색감(다크 와인)이 mockup 베젤 없이 노출됨.

**해결**: A1·A2에 C 유형과 동일 mockup 패턴 적용:
```js
const inst = mockMaster.createInstance();  // 338:3224 원페이지 mockup
inst.rescale(slot.width / inst.width);
inst.x = slot.x; inst.y = slot.y;
inst.effects = slot.effects;  // 보라 글로우 effect 전파 (가이드 §3.1)
frame.appendChild(inst);

const screen = findScreen(inst);  // 비율 0.4535 매칭 rect
screen.fills = [{ type: "IMAGE", scaleMode: "FILL", imageHash }];

slot.fills = []; slot.strokes = [];  // placeholder 정리
```

**룰 갱신 필요** (P1):
- [[1-1-4. 검수 체크리스트]] §자주 놓치는 추가 — "A 유형 VISUAL_SLOT은 자식 0개 빈 frame — 자동화가 mockup instance(338:3224) + screen rect fill 필수. C 유형과 동일 패턴. VISUAL_SLOT 자체에 IMAGE FILL ❌"

### 사고 #4 — 강조어 char count 오류 (9 vs 11) ⭐ NEW (사용자 지적으로 발견)

**증상**: 사용자 지적 — A2에서 "[1:1 개인화 초] 이렇게 단어가 끊겨서 강조색상이 들어갔어".

**원인**: 강조어 "1:1 개인화 초대장"을 빌드 코드에서 `EMPH = 9`로 셈했는데 **정확한 char count는 11**:
- 1, :, 1, (space), 개, 인, 화, (space), 초, 대, 장 = **11자**

`setRangeFills(0, 9, [PURPLE])`이 적용되면서 "1:1 개인화 초"까지만(9자) 보라색 → "대장" 흰색 → 의미 단위 잘림 (§텍스트 절대원칙 ④ 위반).

**해결**: 6안 모두 `setRangeFills(0, 11, [PURPLE])` 재적용 + TITLE 본문 fill을 흰색으로 reset 후 0~11 보라 재적용 (이전 흔적 제거).

**룰 갱신 필요** (P1):
- [[1-1-4. 검수 체크리스트]] §0 ⑤ + §자주 놓치는 #11 — **"강조어 char count는 한글 자모 단위가 아니라 UTF-16 char 단위. 빌드 전 `Array.from(emphasis).length` 또는 `emphasis.length`로 정확히 측정 + 빌드 시 console.log로 검수"** 추가
- [[1-1-4. 검수 체크리스트]] ④ "강조 영역 1개 / 의미 단위" 항목에 "강조어 char count = 실제 setRangeFills end 위치인지 빌드 후 시각 확인"

**원인**: Figma children 배열 마지막이 z-top. 자동화 빌드 코드에서 텍스트 → DECO placeholder → crown instance → mockup instance 순으로 추가 → mockup이 가장 위 (z-top) → 데코를 가림.

**해결**: 빌드 후 데코 instance를 `frame.appendChild(deco)`로 다시 추가 → children 마지막 → z-top 복원.

**룰 정착**:
- [[1-1-4. 검수 체크리스트]] §자주 놓치는 **#12 신설** — "mockup·DECO instance z-index 순서 — DECO는 항상 z-top". 표준 children 순서표 + 자동화 안전 패턴 의사코드 포함.
- [[1-1-3. 이미지 규칙|1-3. 이미지 규칙]] **§1.2.b 신설** — z-index 표준 순서 + 자동화 안전 패턴. §1.2.a 의사코드도 `frame.appendChild(deco)` 패턴으로 동기화.

### 사고 #7 — use_figma MCP instance child fill mutation 적용 안 됨 ⭐⭐⭐ NEW (사용자 지적)

**증상**: A1·A2·B1·B2의 mockup instance 안 screen rect에 viewer hash 적용했는데 화면에 mockup 마스터의 기본 image가 그대로 보임. fill 변경이 적용 안 됨. 사용자 지적 — "캡쳐 화면을 목업에 정확히 넣지 못하고 있어" + "백그라운드 색감이 다 날라갔는데 다시 확인해줘".

**원인**: use_figma MCP 환경 특수 제약 — `mockInst.findAll(n => ...)` 또는 `mockInst.findOne(...)`으로 얻은 instance child reference에 `.fills = [...]` 적용해도 instance override가 작동 안 함. children 자체가 read-only-like reference처럼 동작.

**해결 패턴** ⭐:
```js
// ❌ 작동 안 함 (instance child reference로 mutate)
const screen = mockInst.findOne(n => n.fills?.some(f => f.type === "IMAGE"));
screen.fills = [{ type: "IMAGE", imageHash: HASH }];  // 적용 X

// ⭕ 작동함 (ID 추출 → getNodeByIdAsync 재취득 → mutate)
let screenId = null;
for (const c of mockInst.children) {
  if (c.fills?.some(f => f.type === "IMAGE")) { screenId = c.id; break; }
}
const screen = await figma.getNodeByIdAsync(screenId);
screen.fills = [{ type: "IMAGE", imageHash: HASH }];  // 적용 ⭕
```

**룰 정착**: [[1-1-4. 검수 체크리스트]] §use_figma MCP 직접 모드 — 제약 표에 행 추가 + "instance child mutate 패턴" 별도 절 신설. 사고 사례 인용.

**적용 범위**: A·B 유형 mockup screen rect fill / C 유형 멀티 mockup 3개 screen fill / 모든 instance 자식 노드 mutation.
