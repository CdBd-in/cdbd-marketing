# 🚨🚨🚨 텍스트 삽입 절대 원칙 (사고 최다 발생 지점)

> **여기서 사고가 가장 많이 난다.** 다른 모든 항목보다 먼저, 매 작업마다 이 3가지부터.

## ① 줄 나누기 → **무조건 의미 단위로**
- 어절·구문 단위로 끊기. 의미가 흐트러지는 위치에서 줄바꿈 ❌
- 강조어는 한 줄 안에 통째로. 두 줄에 걸치지 않기.
- ⛔ **원본 텍스트 변경 금지** — `\n` **추가만** 허용. 쉼표·마침표·느낌표·물음표·글자·띄어쓰기 일체 **추가·삭제·변경 ❌**. 받은 타이틀을 그대로 쪼개기만 한다. (2026-06-04 사고: 쉼표 임의 추가 → 임의 삭제 → 결국 원본 그대로 룰로 단순화)

## ② 어절이 중간에 잘리면 안 됨 ⛔
- "고객도 / 지치는 전화" ✅ / "고객도 지치는 / 전화" ✅
- "고객도 지치는 전 / 화 핑퐁" ❌ ← 자동 줄바꿈에 맡기면 이 사고 남
- 방어: `\n` 명시 + 각 줄 폭 ≤350px 실측 검수 + `textAutoResize=HEIGHT` + `node.resize(350)`

## ③ 최대한 **2-3줄 안에** 정렬
- 기본: **2-3줄**. 
- **예외 — 4줄로 늘리는 유일한 조건**: 2-3줄로 정렬했는데 이미지(VISUAL_SLOT / EDITOR_SLOT / 보조 데코)와 겹칠 것 같을 때.
  - 충돌 검증식: `줄수 × 46 + y_start ≤ 다음 슬롯 y_start`
  - 충돌 시 → 4줄로 분산 (5줄 이상은 ❌)

9. 🔴 **viewer ↔ mockup 매칭 — 사람이 브라우저로 보고 파악 필수** (2026-06-12 추가, ⭐ 중요) — **자동 캡처만으로 매칭 결정하지 말 것**. Claude는 viewer URL을 받으면 자동으로 Microlink 캡처에 의존하지 말고, **viewer를 사람이 브라우저 열어서 보는 것처럼 다음 항목을 직접 파악**한 후 mockup·캡처 정책 결정:
   1. **페이지 수**: 단일 페이지 (스크롤형) vs 멀티페이지 (swiper)
   2. **구조**: hero 위치 / 상품 페이지 위치 / 페이지네이션 형태 / 페이지별 컨텐츠
   3. **mockup 매칭 필수**:
      - **단일 페이지 viewer** → **원페이지 mockup `75:34`** ([[1-3-1. 이미지 규칙]] §1.1.a)
      - **멀티페이지 viewer (swiper)** → **멀티페이지 mockup `1:1370`** ⭐ — 가이드 §1.1.a "카탈로그·룩북·매거진" 매핑 표 그대로
      - ❌ 멀티페이지 viewer를 원페이지 mockup에 fill = 의미 매칭 어긋남 (시각적으로는 작동해도 메시지 부합 안 함)
   4. **캡처 결과 시각 확인**: 자동 캡처 후 mockup fill 전에 PNG를 직접 보고 페이지네이션·상단 빈 영역·하단 잘림 등 확인 → 필요 시 PIL 후처리 ([[1-3-2. 이미지 출처]] §2 멀티페이지 정책)

   **사고 사례** (2026-06-12 AIC 카탈로그 시안): 멀티페이지 viewer(lookbook·newarrival·online_lookbook)를 원페이지 mockup(75:34) + 멀티페이지 mockup(1:1370) **두 가지 mockup에 동시 fill**해서 "변형 2안" 만들었으나 사용자가 지적: "멀티페이지는 무조건 멀티페이지 mockup". 원페이지 mockup 시안 삭제 → 멀티페이지 mockup만 유지. 룰 정착.

   **표준 워크플로우**:
   ```
   viewer URL → 직접 분석 (페이지 수·구조)
              ↓
   mockup 종류 결정 (75:34 or 1:1370)
              ↓
   캡처 전략 (?page=N · PIL crop 필요 여부)
              ↓
   Microlink 캡처 → 시각 확인 → 필요 시 후처리 → upload_assets → fill
   ```

## 📋 자동화 지원 현황 (2026-06-04)

자동화는 두 단계로 나뉩니다:
- **슬롯 fill 자동화**: 슬롯 clone → 텍스트/이미지/색상 자동 적용
- **이미지 자동 소싱**: 어디서 이미지를 가져올지 (자동 vs 수동 imageHash 입력)

| 유형 | 슬롯 fill | 이미지 자동 소싱 | 비고 |
|------|----------|-----------------|------|
| **A. 목업** | ✅ `applyMockup()` (목업 인스턴스 + CROP+imageTransform) | ✅ 완전 자동 | **Microlink + cdbd.in viewer 캡처 자동** (가이드 §3.1·§2 17개 매핑) — 무료 50 req/day |
| **B. 목업+에디터** | ✅ `applyEditor()` (EDITOR_SLOT FIT fill) + `applyMockup()` | ❌ 수동 입력 | 슬롯 fill 완성 (2026-06-01). 에디터 캡처 (Playwright) 자동 호출 미구현 |
| **C. 멀티 목업** | ⚠️ VISUAL_SLOT_1/2/3 처리 별도 필요 (플러그인 미구현) / **use_figma 직접 모드 ✅ 2026-06-12 첫 시험 통과** | ❌ 수동 입력 (use_figma + upload_assets 6장 POST 패턴) | viewer 2-3개 자동 캡처는 `viewport.height=900` + `full-page=false` 정책 사용 (hero 캡처) — [[1-3-2. 이미지 출처]] §2 |
| **D. 3D 아이콘** | ✅ `apply3DIcon()` (VISUAL_SLOT FIT fill) | ⚠️ 부분 자동 | envelope·calendar·crown·shield·globe·magic-wand 자동 / card·book·chat-bubble·pen·chart-up 미등록 |
| **E. 배경** | ✅ `applyBackground()` (BG_SLOT opacity 20%) + 보조 VISUAL_SLOT | ✅ 완전 자동 | Lexica AI 생성 배경 + Thiings 3D 자동 다운로드 |

> 💡 **수동 imageHash 입력 방식**: 플러그인 UI의 "변형 매트릭스 (JSON 배열)"에 `{"slotId": "...", "imageHash": "...", "name": "..."}` 형식으로 입력하면 모든 유형이 작동.
> 📌 **외부 인프라 요구사항**: A/B/C 유형의 완전 자동화는 Microlink/Playwright API 호출 코드 추가 필요 (외부 서비스 호출은 가능하나 plugin code에 미구현).

## 🛠️ use_figma MCP 직접 모드 — 제약사항 (2026-06-12 신규)

> 플러그인이 미지원하는 슬롯 유형(현재 C·E 일부)을 Claude가 use_figma로 직접 빌드할 때 적용. 일반 plugin API와 동작이 다른 부분만 정리.

| API | plugin (정상) | use_figma MCP | 대체 |
|-----|--------------|---------------|------|
| `figma.getNodeById(id)` | ✅ sync | ❌ cross-page 미지원 | **`await figma.getNodeByIdAsync(id)`** |
| `figma.loadAllPagesAsync()` | ✅ | ❌ "not supported" | 제거 — 페이지 순회는 `figma.root.children` 직접 |
| `figma.currentPage = page` | ✅ | ❌ "not supported" | **`await figma.setCurrentPageAsync(page)`** |
| `figma.createImageAsync(url)` | ✅ (manifest 등록 도메인) | ❌ "not supported" | `upload_assets` MCP 도구 + curl POST → response 의 `imageHash` 사용 |
| `fetch(url)` | ✅ manifest 등록 시 | ❌ "fetch is not defined" | 동일 — `upload_assets` 패턴 |
| `throw new Error()` | (변경 적용 후 throw) | ⚠️ 변경 rollback 가능성 — 변경/검증 분리 필요 | 검증은 별도 호출, 변경 함수에서는 throw 회피 |

**자산 업로드 표준 패턴**:
1. PNG 캡처 → vault `.temp/` 폴더 저장
2. `upload_assets` MCP 호출 (count 최대 5) → 단일사용 submitUrl 받기
3. 각 PNG를 `curl -F file=@x.png` 로 POST → response의 `imageHash` 추출
4. 업로드는 부산물로 **임시 frame을 currentPage에 생성** → use_figma 안에서 명시적 `remove()` 필요
5. use_figma 코드 안에서 imageHash를 mockup screen rect의 IMAGE fill로 적용
