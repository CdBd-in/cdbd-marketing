# 🚨🚨🚨 시안 제작 사전 0단계 — **입력 분석** (2026-06-18 신설)

> **사전 3원칙(§아래)에 들어가기 전, 입력 형식부터 분석한다.**
> 2026-06-18 룰 전환: 입력이 "타이틀만"이 아니라 **"타이틀 + 본문"**으로 받음. 본문이 유형·자산·강조어 결정의 1차 근거.
> 첫 시험 사례: [[블로그/썸네일/시안 로그/2026-06-18 PDF·플립북 카탈로그의 한계.md]]

## 입력 분석 절차 (사전 3원칙 진입 전 필수)

### ① 입력 형식 확인
- **타이틀 + 본문**: 본문 구조까지 분석에 활용 (이하 절차 전체 적용)
- **타이틀만**: 기존 방식 — 본문 구조 분석 항목은 건너뜀. 단 em dash/강조어 길이 검사는 동일 적용

### ② em dash / marker 분리 검사
- 타이틀 안 `—`(em dash) / `-`(hyphen) / `/`(슬래시) 또는 시리즈명 marker → **SUBTITLE/TITLE 분리 후보**
- marker 있으면 사용자 컨펌 권장 (서브타이틀 슬롯 변형 선택을 결정)
- 원본 텍스트 변경 ❌ — marker는 분리 기호로만 활용, 양옆 공백만 trim

### ③ 본문 구조 분석 → 유형 격상 ([[1-2-1. 레이아웃 규칙]] §1.1 신호어 매칭의 보강)
- **대비 구조** (X vs Y / 한계 vs 해결 / N가지 vs M가지 / 전 vs 후) → **C 멀티 격상** ⭐ 1순위 가능
- **단일 사례 시연** (한 viewer/사이트가 핵심 매칭) → **A 격상**
- **선언·정의·주장** (X란 Y이다 / 진짜 ~ / 왜 ~ ) → **D 격상 후보**
- 본문 신호가 약하면 타이틀 신호어 매칭(§1.1)으로 결정

### ④ 자산 직접 매칭 (가이드 우선)
- 본문이 [[1-3-2. 이미지 출처]] §5.2 17개 viewer 중 하나를 **명백히 가리키면** → 그 viewer를 1순위 자산으로 확정 (추측 ❌)
- 본문 §정의/설명과 viewer §2.x 설명이 1:1 매칭되는 경우만 (예: "문의로 이어지는 동선" ↔ `catalog/oak_table` "제품 정보 전달과 고객 문의 연결")

### ⑤ 강조어 길이 사전 측정 (사고 #1 방지 — 2026-06-18 PDF·플립북 사례)
- **공식**: 한글 강조어 글자 수 × 30px (폰트 size 36 기준) ≤ TITLE width 인지 빌드 전 검사
- **width 기본값**:
  - D/A 슬롯: width 285 (한글 ~9자 fit)
  - C 슬롯: width 266 (한글 ~8자 fit)
- **초과 시 옵션**:
  - C 슬롯: width 460까지 확장 OK (mockup_2 y=199와 시각 분리)
  - D/A 슬롯: width 350까지 확장 — mockup x=300(D) / 366(A) 충돌 검사 (24px 이내 overlap 시각 검수)
  - 모든 옵션 초과 시 fontSize 36 → 32 축소 또는 강조어 단축 (사용자 확인)
- **사례**: 강조어 "진짜 모바일 카탈로그" 10자 × 30 = 300px > width 285 → 자동 wrap이 "진짜 모바일 카탈로 / 그**로**" 어절 중간 잘림. width 350/460 확장으로 해결.

# 🚨🚨🚨 시안 제작 직전 — 사전 3원칙 (사용자 핵심 요구, 2026-06-12 정착)

> **타이틀을 받고 작업을 시작하기 전, 반드시 이 3가지를 의식적으로 확인하고 들어간다.**
> 같은 실수 패턴이 반복돼 사용자가 매번 지적했던 항목 → 룰로 격상.
> 이걸 놓치면 텍스트·스타일 다 맞아도 시안 전체가 단조·일변도 ❌.

## 🔴 ① 레이아웃 다중 — **유형 2~3개 × 각 유형별 1~2안**

- **단일 유형 ❌** — A만 또는 D만 4안 패키지는 금지.
- **유형 결정**: [[1-2-1. 레이아웃 규칙]] §1.1 신호어 매칭으로 1·2순위 유형 필수 선택, 3순위 신호어 명백하면 추가. **단 신호어 매칭이 약한 유형을 억지로 끼우지 않음**.
- **유형별 안 개수**:
  - **A·B·D** (위치 변형 있음): 상단·서브 + 하단·서브 = 2안 / 의미 매칭이 한 위치만 자연스러우면 1안 OK
  - **C** (상단 고정): 1안 (다른 자산 조합으로 2안 가능)
  - **E** (중앙 고정): 다른 자산 2안
- **출력 총량**: **4~6안 (유형 2~3개 × 1~2안)**.
- **사용자가 유형 자체부터 비교** 가능해야 함 — 시안 다양성의 가장 큰 축은 유형.

> ❌ **사례 (반복 지적)**: INHA·MASTERS·PICOHI 모두 A 유형 단일 패키지로 시작 → 사용자 "왜 또 A만이야?" 지적.
> 📌 디테일: §자주 놓치는 #1 / [[1-2-1. 레이아웃 규칙]] §1.1

## 🔴 ② 캡처 영역 — **사람 관점으로 분석 + 안마다 다른 영역**

- **자동 캡처만 보고 결정 ❌** — viewer URL을 받으면 반드시 **사람이 브라우저로 보듯** 페이지 전체 시각 분석.
- 확인 항목:
  1. 페이지 수 (단일 스크롤 vs 멀티페이지 swiper)
  2. 의미 섹션 구조 (hero / 핵심 정보 / RSVP·CTA)
  3. 타이틀이 가리키는 **그 정보**가 viewer의 어느 영역에 있나
- **안마다 다른 영역 사용** — 같은 hero(ty=0)만 반복 ❌. 한 시안에서:
  - 안 1: hero (정체성)
  - 안 2: 핵심 정보 영역 (타이틀 직접 매칭)
  - C 멀티: 3 mockup에 **각각 다른 섹션** (정체성 → 핵심 정보 → 액션) — [[1-3-1. 이미지 규칙]] §1.1.b 섹션 분할 패턴
- **검토 절차**: PNG 시각 확인 → 의미 매칭 평가 → 부합 안 하면 ty 조정 또는 재캡처

> ❌ **사례 (반복 지적)**: INHA A 안 1·2 둘 다 hero(ty=0) 동일 캡처 → 사용자 "다양하게 적용해줘".
> 📌 디테일: §자주 놓치는 #10 / [[1-3-1. 이미지 규칙]] §1.1.b

## 🔴 ③ 3D 아이콘 — **매번 같은 이모지 ❌, 타이틀 매칭 thiings 신규 다운로드**

- **sparkle 무조건 반복 ❌** — calendar / crown / shield / globe 등 **톤 매칭 데코를 1순위**로 ([[1-3-2. 이미지 출처]] §1d 표).
- **3D 아이콘 (D 유형) 시안**: 등록된 envelope·mobile-phone·calendar 등에서 우선 시도 → **없으면 thiings.co에서 신규 슬러그 검증·다운로드** ([[1-3-2. 이미지 출처]] §4.1 절차).
- **타이틀 매칭 thiings 슬러그 추측 패턴**:
  - "모바일 초대장" → `mobile-phone` / `smartphone` / `envelope`
  - "초대장·행사" → `envelope` / `calendar`
  - "프리미엄·VIP" → `crown`
  - "안전·보안" → `shield`
  - "AI·자동화" → `magic-wand` / `robot`
  - 슬러그 검증: `curl -s "https://www.thiings.co/things/{slug}" | grep "vercel-storage"` → 200이면 PNG URL 확보
- **다양성 안 1 / 안 2**: 같은 시안에 2안 만들 때 각 안에 **다른 3D 아이콘** 적용 (예: 안 1 mobile-phone / 안 2 envelope).

> ❌ **사례 (반복 지적)**: INHA 이전 시안들이 calendar·shield 반복 → 사용자 "thiings에서 다운받아 써줘". INHA에서 mobile-phone 신규 등록으로 해결.
> 📌 디테일: §자주 놓치는 #7 / [[1-3-2. 이미지 출처]] §4.1·§5.4

# 🚨🚨🚨 텍스트 삽입 절대 원칙 (사고 최다 발생 지점)

> **여기서 사고가 가장 많이 난다.** 다른 모든 항목보다 먼저, 매 작업마다 이 3가지부터.

## ① 줄 나누기 → **무조건 의미 단위로**
- 어절·구문 단위로 끊기. 의미가 흐트러지는 위치에서 줄바꿈 ❌
- 강조어는 한 줄 안에 통째로. 두 줄에 걸치지 않기.
- ⛔ **원본 텍스트 변경 금지** — `\n` **추가만** 허용. 쉼표·마침표·느낌표·물음표·글자·띄어쓰기 일체 **추가·삭제·변경 ❌**. 받은 타이틀을 그대로 쪼개기만 한다. (2026-06-04 사고: 쉼표 임의 추가 → 임의 삭제 → 결국 원본 그대로 룰로 단순화)

## ② 어절이 중간에 잘리면 안 됨 ⛔
- "고객도 / 지치는 전화" ✅ / "고객도 지치는 / 전화" ✅
- "고객도 지치는 전 / 화 핑퐁" ❌ ← 자동 줄바꿈에 맡기면 이 사고 남
- 방어: `\n` 명시 + 각 줄 폭 ≤350px 실측 검수 + `textAutoResize=HEIGHT` + `node.resize(350)`

## ③ 최대한 **2-3줄 안에** 정렬
- 기본: **2-3줄**. 
- **예외 — 4줄로 늘리는 유일한 조건**: 2-3줄로 정렬했는데 이미지(VISUAL_SLOT / EDITOR_SLOT / 보조 데코)와 겹칠 것 같을 때.
  - 충돌 검증식: `줄수 × 46 + y_start ≤ 다음 슬롯 y_start`
  - 충돌 시 → 4줄로 분산 (5줄 이상은 ❌)

   - **자동 측정**:
     ```js
     const imgSize = await figma.getImageByHash(hash).getSizeAsync();
     const yScale = (screen.height / screen.width) / (imgSize.height / imgSize.width);
     screen.fills = [{ type: "IMAGE", imageHash: hash, scaleMode: "CROP",
                       imageTransform: [[1, 0, 0], [0, yScale, ty]] }];
     ```

| API | plugin (정상) | use_figma MCP | 대체 |
|-----|--------------|---------------|------|
| `figma.getNodeById(id)` | ✅ sync | ❌ cross-page 미지원 | **`await figma.getNodeByIdAsync(id)`** |
| `figma.loadAllPagesAsync()` | ✅ | ❌ "not supported" | 제거 — 페이지 순회는 `figma.root.children` 직접 |
| `figma.currentPage = page` | ✅ | ❌ "not supported" | **`await figma.setCurrentPageAsync(page)`** |
| `figma.createImageAsync(url)` | ✅ (manifest 등록 도메인) | ❌ "not supported" | `upload_assets` MCP 도구 + curl POST → response 의 `imageHash` 사용 |
| `fetch(url)` | ✅ manifest 등록 시 | ❌ "fetch is not defined" | 동일 — `upload_assets` 패턴 |
| `throw new Error()` | (변경 적용 후 throw) | ⚠️ 변경 rollback 가능성 — 변경/검증 분리 필요 | 검증은 별도 호출, 변경 함수에서는 throw 회피 |
| **`instance.findAll(...)[i].fills = [...]`** ⭐ NEW 2026-06-19 | ✅ direct mutation | ❌ instance 자식 reference로 fills 변경이 적용 안 됨 (override 누락) | **children 순회 → ID 추출 → `await figma.getNodeByIdAsync(childId)` 재취득 후 mutate** ⭐ |

### 🆕 use_figma 제약 — instance child mutate 패턴 (2026-06-19 사고 사례)

**증상**: A·B 유형 빌드에서 mockup instance(75:34) 자식 screen rect에 viewer 이미지 fill 적용했는데 화면에 mockup 마스터의 기본 image가 그대로 보임. fill 변경이 적용 안 됨.

**원인**: `mockInst.findAll(n => ...)` 또는 `mockInst.findOne(...)`으로 얻은 child reference에 `.fills = [...]` 적용해도 instance override가 작동 안 함. use_figma MCP 환경 특수 제약.

**해결 패턴** ⭐:
```js
// ❌ 작동 안 함 (instance child reference)
const screen = mockInst.findOne(n => n.fills?.some(f => f.type === "IMAGE"));
screen.fills = [{ type: "IMAGE", imageHash: HASH }];  // 적용 X

// ⭕ 작동함 (ID 재취득 후 mutate)
let screenId = null;
for (const c of mockInst.children) {
  if (c.fills?.some(f => f.type === "IMAGE")) {
    screenId = c.id; break;
  }
}
const screen = await figma.getNodeByIdAsync(screenId);
screen.fills = [{ type: "IMAGE", imageHash: HASH }];  // 적용 ⭕
```

**적용 범위**:
- A·B 유형 mockup instance(75:34) screen rect fill
- C 유형 mockup instance 3개 각각 screen fill
- 모든 instance 자식 노드 mutation 시 동일 패턴 권장

**사고 사례**: 2026-06-19 VIP 1:1 개인화 시안 A1·A2·B1·B2 — `mockInst.findAll` 패턴으로 빌드 후 시각 검수에서 screen에 잘못된 image 보임. children 순회 + `getNodeByIdAsync(screenId)` 패턴으로 해결.

**자산 업로드 표준 패턴**:
1. PNG 캡처 → vault `.temp/` 폴더 저장
2. `upload_assets` MCP 호출 (count 최대 5) → 단일사용 submitUrl 받기
3. 각 PNG를 `curl -F file=@x.png` 로 POST → response의 `imageHash` 추출
4. 업로드는 부산물로 **임시 frame을 currentPage에 생성** → use_figma 안에서 명시적 `remove()` 필요
5. use_figma 코드 안에서 imageHash를 mockup screen rect의 IMAGE fill로 적용
