## 7. 작업 흐름 인사이트 (타이틀만 vs 타이틀+내용 회고)

> 사용자가 직접 회고를 요청 — "타이틀만 주어졌을 때랑 만드는 과정에서 다른점이 뭐였어?"

### 7.1. 정보 밀도가 달라짐

| 단계 | 타이틀만 (2026-06-14) | 타이틀+내용 (2026-06-18) |
|---|---|---|
| 유형 결정 | 신호어 매칭이 거의 전부, 사용자가 "C도 넣어줘" 명시 요청 필요 | 본문 대비 구조가 C 1순위로 자동 격상, 사용자 요청 불필요 |
| 자산 매칭 | 톤 기반 추측 (corporate? sales?) → hero 캡처 후 시각 평가 | 본문이 §5.2 어휘를 직접 사용 → 추측 단계 사라짐, 가설 → 확정 |
| 강조어 | 짧은 단어 1개(4자 "진짜 이유") | 본문 핵심 정의 구 단위(10자 "진짜 모바일 카탈로그") |
| 3D 다양화 | brainstorming (mobile-phone, wallet) | 본문 §2·§4 의미 대비에서 자동 도출 (document vs mobile-phone) |
| C 멀티 차별 축 | "다양성"이 목적 | 본문 구조에서 의미 축 자동 분리 (산업 vs 활용) |

### 7.2. 의사결정 횟수가 줄어듦
사전에 분석 보고서를 풍부하게 만들고 컨펌만 3개 받음(em dash / 활용 범위 / 룰 정착). 빌드 중 자산 관련 추가 질문 없음.

### 7.3. 부작용 — 강조어 길어져서 새 사고 유발
강조어가 단어 → 구 단위로 길어진 게 정상이 되니 슬롯 width 한계 초과가 잦아질 수 있음. → §자주 놓치는 #11로 룰 박음 ("강조어 길어지는 게 정상 → 빌드 전 무조건 측정").

### 7.4. 룰 정착이 가능해짐
본문 ↔ 가이드(§5.2 viewer 설명) ↔ 시안 자산이 1:1 추적 가능 → 명확한 절차로 룰화 가능. 타이틀만일 땐 매번 추측 패턴이라 룰 격상 어려웠음.
